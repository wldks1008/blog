<h2>증가하는 데이터</h2>
<p><span>서비스를 운영하다 보면 데이터가 계속 쌓이게 된다. </span><span>처음에는 데이터가 많지 않기 때문에 조회 쿼리를 실행해도 빠르게 결과를 가져올 수 있다. 하지만 서비스가 성장하면서 데이터가 수천만 건, 수억 건 단위로 늘어나면 조회 성능이 이전보다 느려지는 상황이 발생할 수 있다.</span></p>
<p><span>물론 데이터가 많다는 이유만으로 모든 쿼리가 느려지는 것은 아니다. 조회 조건이나 실행 계획, 인덱스 구성, 버퍼 풀의 캐시 적중률 등 다양한 요소가 성능에 영향을 미친다. </span><span>다만 조회해야 하는 데이터의 범위가 넓거나 많은 데이터를 읽어야 하는 쿼리라면 데이터가 증가하면서 처리해야 하는 페이지의 수도 늘어날 수 있다.</span></p>
<p><span>그렇다면 <b>데이터가 계속 쌓이는 것을 방지하기 위해 오래된 데이터를 삭제하면 조회 성능도 개선할 수 있을까? </b></span></p>
<p><span>단순히 생각하면 불필요한 데이터가 줄어들기 때문에 조회 성능도 좋아질 것 같다. </span><span>하지만&nbsp;</span><span>데이터를 삭제하는 것과 데이터가 저장된 공간을 효율적으로 사용하는 것은 서로 다른 문제다.</span></p>
<h2><span>데이터를 삭제하면 디스크 공간도 줄어들까?</span></h2>
<h3><span>DELETE와 디스크 공간</span></h3>
<p><span>DELETE 쿼리를 실행하면 조건에 해당하는 데이터가 삭제된다. </span></p>
<p><span><span>그렇다면 <b>삭제한 데이터가 차지하던 디스크 공간도 즉시 반환될까?&nbsp; </b></span></span>일반적으로는 그렇지 않다.</p>
<p>&nbsp;</p>
<p><span>InnoDB는 테이블의 데이터를 페이지(Page)라는 단위로 관리한다. 기본 페이지 크기는 16KB이며, 테이블 데이터와 관련된 정보가 이러한 페이지에 저장된다.</span></p>
<p>&nbsp;</p>
<p>데이터를 삭제하면 해당 레코드는 곧바로 사라지지 않고, 먼저 삭제 표시(delete-mark)만 된다. 이때 롤백과 다른 트랜잭션의 일관된 읽기(MVCC)를 위해 변경 이전 버전이 undo log에 함께 기록된다. 삭제한 트랜잭션이 롤백될 수도 있고, 삭제 이전 시점의 데이터를 보고 있는 다른 트랜잭션이 있을 수도 있기 때문이다.</p>
<p>이후 어떤 트랜잭션도 이전 버전을 필요로 하지 않게 되면, InnoDB의 백그라운드 스레드인 Purge가 삭제 표시된 레코드를 페이지에서 실제로 제거하고 관련 undo log도 정리한다. Purge는 비동기로 수행되므로 DELETE가 끝난 직후에는 레코드가 페이지에 남아 있을 수 있다.</p>
<p>다만 Purge가 하는 일은 레코드를 페이지에서 제거하는 데까지다. <b>제거된 레코드가 차지하던 공간은 페이지 안의 빈 공간으로 남을 뿐, 운영체제에 반환되지는 않는다</b>. 이 빈 공간은 이후 INSERT 등으로 새 데이터가 들어올 때 InnoDB가 재사용한다.</p>
<p><figure class="imageblock widthContent"><span><img height="470" src="https://blog.kakaocdn.net/dn/bczd3E/dJMcagHDIAB/TyWafccLnJ29CfQ7KbfrA1/img.png" width="1500" /></span></figure>
</p>
<p>예를 들어 100개의 레코드가 저장된 페이지에서 90개를 삭제했다고 가정해 보자. Purge가 끝나면 90개의 레코드는 페이지에서 사라지지만, 페이지 자체는 그대로 유지되고 내부에 빈 공간만 늘어난다. 이후 새로운 데이터가 들어오면 InnoDB는 이 빈 공간을 다시 사용한다.</p>
<p>결국 데이터를 삭제해도 테이블이 사용하는 파일 크기는 그대로일 수 있다. 줄어든 것은 데이터이고, 파일 크기는 빈 공간이 재사용되는 만큼 유지될 뿐이다.</p>
<p>&nbsp;</p>
<p><span>즉, </span><b><span>데이터를 삭제해도 테이블이 사용하는 파일 크기는 그대로 유지될 수 있으며, 남은 빈 공간은 이후 저장되는 데이터가 재사용</span></b><span>하는 방식이다.</span></p>
<h3><span>삭제한 공간은 어디에 남을까?</span></h3>
<p><span>데이터가 저장된 페이지 내부에 여유 공간이 생기는 것은 자연스러운 현상이다. </span><span>문제는 삭제 이후에도 테이블의 데이터가 기존과 비슷한 수의 페이지에 분산되어 남아 있거나, 데이터가 차지하는 공간에 비해 페이지를 비효율적으로 사용하게 되는 경우다.</span></p>
<p>&nbsp;</p>
<p><span>예를 들어 다음과 같은 상황을 생각해 보자.</span></p>
<p><figure class="imageblock widthContent"><span><img height="670" src="https://blog.kakaocdn.net/dn/K1FpB/dJMcacL1k82/P5FiyNpgL8G9HsoSNpjSS0/img.png" width="1582" /></span></figure>
</p>
<p>삭제하기 전에는 10개의 페이지에 데이터가 저장되어 있었다고 가정해 보자.</p>
<p>이후 대부분의 데이터를 삭제했지만 남은 데이터가 여전히 여러 페이지에 흩어져 있다면, 각 페이지에는 사용되지 않는 빈 공간이 많이 남는다. 이 경우 같은 데이터를 조회하더라도 접근해야 하는 페이지 수가 불필요하게 많아진다. 반대로 남은 데이터를 더 적은 수의 페이지에 모아 저장할 수 있다면 조회 시 접근하는 페이지 수도 줄어든다.</p>
<blockquote>삭제 후 항상 이런 상태가 되는 것은 아니다. InnoDB는 삭제로 생긴 빈 공간을 이후 INSERT에서 재사용하고, 페이지가 많이 비면 인접한 페이지와 병합하기도 한다. 그래서 데이터를 삭제했다고 해서 반드시 페이지가 듬성듬성 남는 것은 아니다. 그럼에도 대량의 데이터를 삭제한 뒤 테이블이 차지하는 공간이 실제 데이터 크기에 비해 지나치게 크다면, OPTIMIZE TABLE 명령으로 테이블을 재구성해 저장 공간과 페이지 구성을 개선할 수 있다.</blockquote>
<p><span>이처럼 데이터가 삭제된 뒤에도 저장 공간이 비효율적으로 남아 있는 상황을 이해할 때 <b>단편화(Fragmentation)</b>라는 개념을 살펴볼 필요가 있다.</span></p>
<h2><span>단편화와 Disk I/O의 상관관계</span></h2>
<h3><span>페이지 단위의 데이터 읽기</span></h3>
<p><span>InnoDB에서</span><span>&nbsp;데이터를 조회할 때는 필요한 레코드만 정확히 디스크에서 읽어 오는 것이 아니라, 해당 레코드가 포함된 페이지를 읽는다. </span><span>물론 필요한 페이지가 버퍼 풀에 있다면 디스크에 접근하지 않고 메모리에서 데이터를 읽을 수 있지만,</span><span> 필요한 페이지가 버퍼 풀에 없다면 저장 장치에서 페이지를 읽어 와야 한다.</span><span></span></p>
<p><span>따라서 조회 성능을 이해할 때는 단순히 데이터가 몇 건인지뿐만 아니라, </span><b><span>조회 과정에서 몇 개의 페이지에 접근해야 하는지</span></b><span>도 중요하다.</span></p>
<p>&nbsp;</p>
<p><span>여기서 단편화와 조회 성능의 관계를 살펴볼 수 있다. </span></p>
<p><span>데이터를 삭제하기 전에는 10개의 페이지에 레코드가 고르게 저장되어 있었다고 가정하자. </span><span>이후 전체 데이터의 90%를 삭제했다.</span></p>
<p><figure class="imageblock widthContent"><span><img height="768" src="https://blog.kakaocdn.net/dn/bKgZlb/dJMcacL6Ui7/KFsZwovs01vpk6ZzYol9oK/img.png" width="1846" /></span></figure>
</p>
<p><span>삭제가 끝난 뒤 남은 데이터가 기존 10개의 페이지에 분산되어 있다면, 조회 과정에서 여전히 여러 페이지에 접근해야 할 수 있다.</span></p>
<p style="color: #333333; text-align: start;"><span>반면 테이블을 재구성하면서 남은 데이터가 1개의 페이지에 들어갈 수 있도록 저장 공간이 정리되었다면, 동일한 데이터를 조회하는 데 필요한 페이지 접근 수가 줄어들 수 있다. </span><span>이러한 경우에는 데이터를 재구성한 이후 조회 성능이 개선될 가능성이 있다.</span><span></span></p>
<blockquote>페이지 내부에 빈 공간이 많다는 사실만으로 디스크 I/O가 반드시 증가하는 것은 아니다.<br /><span>빈 공간이 많더라도 쿼리가 동일한 수의 페이지에 접근한다면, 빈 공간 자체가 추가적인 페이지 읽기를 발생시키는 것은 아니다. </span><span>성능에 영향을 주는 핵심은 <b>삭제된 공간의 존재 자체보다는 데이터가 실제로 몇 개의 페이지에 저장되어 있는지</b>, 조회 과정에서 <b>몇 개의 페이지를 읽어야 하는지</b>, 그리고 <b>필요한 페이지가 메모리에 캐시되어 있는지</b>에 있다. </span><span>따라서 단편화가 심하다는 이유만으로 모든 조회 쿼리가 느려진다고 단정할 수는 없다.<br /></span></blockquote>
<h4>다량의 데이터 삭제 후, 확인해야 할 지표</h4>
<p><span>대량의 데이터를 삭제하면 테이블의 실제 레코드 수는 크게 줄어들 수 있다. </span><span>하지만 테이블이 사용하는 페이지 수나 디스크 공간이 같은 비율로 줄어드는 것은 아니다. 앞서 설명한대로&nbsp;</span><span>삭제된 공간이 InnoDB 내부에서 재사용 가능한 상태로 남을 수 있기 때문이다.</span></p>
<p><span>이때 테이블의 페이지 구성이 비효율적이라면 남은 데이터의 조회 과정에서도 불필요하게 많은 페이지에 접근할 가능성이 있다.</span></p>
<p><span>따라서 대량 삭제 이후에는 단순히 삭제된 데이터 건수만 확인할 것이 아니라, 실제 테이블 크기와 조회 쿼리의 실행 계획, 읽기 작업량 등을 함께 살펴보는 것이 좋다.</span><span></span></p>
<h2><span>테이블 재구성 방법</span></h2>
<h3><span><span>OPTIMIZE TABLE</span></span></h3>
<p><span>MySQL에서는 InnoDB 테이블을 재구성하기 위해 </span><span>OPTIMIZE TABLE</span><span>을 사용할 수 있다.</span></p>
<pre class="sql" id="code_1793624195456"><code>OPTIMIZE TABLE orders;</code></pre>
<p><span><a href="https://dev.mysql.com/doc/refman/8.4/en/optimizing-innodb-storage-layout.html" rel="noopener" target="_blank">InnoDB에서 이 명령은 일반적으로 테이블을 재구성하는 작업으로 처리된다</a>. 실제 동작은 MySQL 버전과 테이블 설정 등에 따라 달라질 수 있다.</span></p>
<p><span>테이블을 재구성하면 데이터를 다시 배치하면서 페이지 구성이 개선될 수 있다. 그 결과 테이블이 사용하는 페이지 수가 줄어들거나, 삭제 이전보다 저장 공간을 효율적으로 사용할 수 있다. </span><span>또한 재구성 결과에 따라 테이블의 파일 크기가 줄어들 수도 있다.</span></p>
<p><span>다만 </span><span>OPTIMIZE TABLE</span><span>을 실행한다고 해서 반드시 디스크 공간이 특정 비율만큼 줄어들거나, 모든 조회 쿼리의 성능이 개선되는 것은 아니다. </span><span>이미 데이터가 효율적으로 저장되어 있거나, 조회 성능의 병목이 다른 곳에 있다면 기대한 만큼의 효과가 나타나지 않을 수 있다.</span></p>
<p><span>따라서 </span><span>OPTIMIZE TABLE</span><span>은 무조건 실행해야 하는 작업이라기보다, 실제 테이블의 상태와 작업 목적을 고려해 선택해야 하는 작업이다.</span></p>
<h4><span>대량 삭제 직후 실행해도 괜찮을까?</span></h4>
<p><span>대량의 데이터를 삭제한 뒤 테이블을 재구성하면 저장 공간을 정리하는 데 도움이 될 수 있다. </span><span>하지만 <b>테이블 재구성 자체에도 상당한 비용이 발생</b>할 수 있다.</span></p>
<p><span>테이블의 크기에 따라 많은 디스크 I/O와 CPU 자원이 필요할 수 있으며, 작업 과정에서 추가 디스크 공간도 요구될 수 있다. 또한 작업 중 테이블에 대한 동시 접근이나 잠금, 서비스 지연 등에 영향을 줄 수 있으므로 운영 환경에서는 작업 방식과 영향 범위를 확인해야 한다.</span></p>
<p><span>특히 수천만 건 이상의 데이터를 삭제한 직후라면 삭제 작업과 테이블 재구성 작업이 데이터베이스에 주는 부하를 함께 고려해야 한다.</span></p>
<p><span>따라서 운영 환경에서 대량 삭제를 진행할 때는 다음 사항을 확인하는 것이 좋다.</span></p>
<ol>
<li><span>삭제 대상 데이터와 예상 삭제 건수를 사전에 확인한다.</span></li>
<li><span>대량 삭제로 인해 발생할 데이터베이스 부하를 고려한다.</span></li>
<li><span>삭제 이후 테이블의 실제 크기와 조회 성능을 확인한다.</span></li>
<li><span>공간 재구성이 필요하다면 </span><span>OPTIMIZE TABLE</span><span>의 실행 비용과 운영 영향을 검토한다.</span></li>
<li><span>작업 전후의 쿼리 실행 계획과 성능 지표를 비교한다.</span></li>
</ol>
<p><span>단순히 데이터를 많이 삭제했다는 이유만으로 곧바로 테이블을 재구성하기보다는, 실제로 저장 공간이나 조회 성능에 문제가 있는지 확인한 뒤 결정하는 것이 좋다.</span></p>
<h2><span>정리</span></h2>
<p><span>데이터가 많아지면 일부 조회 쿼리에서 처리해야 하는 데이터와 페이지 수가 증가하면서 성능이 저하될 수 있다. 이러한 상황에서는 오래된 데이터를 삭제해 테이블의 데이터 증가를 제한하는 것이 도움이 될 수 있다. </span></p>
<p><span>하지만 데이터를 삭제한다고 해서 테이블의 저장 공간이 즉시 줄어들거나, 조회 성능이 반드시 개선되는 것은 아니다.</span></p>
<p>&nbsp;</p>
<p><span>InnoDB는 페이지 단위로 데이터를 관리하며, 삭제된 공간은 내부적으로 재사용될 수 있다. 또한 페이지 내부의 여유 공간이 많다는 사실만으로 추가적인 디스크 I/O가 발생하는 것도 아니다. </span><span>실제 성능에 영향을 주는 것은 조회 과정에서 접근해야 하는 페이지 수, 버퍼 풀의 캐시 적중 여부, 그리고 데이터가 저장된 구조와 쿼리의 실행 방식이다.</span></p>
<p>&nbsp;</p>
<p><span>따라서 대량의 데이터를 삭제한 뒤에는 단순히 데이터 건수가 줄어든 것만 확인할 것이 아니라, 테이블의 저장 공간과 실제 조회 성능도 함께 확인할 필요가 있다. </span><span>필요하다면 </span><span>OPTIMIZE TABLE</span><span>을 통해 테이블을 재구성할 수 있지만, 작업에 따른 리소스 사용량과 운영 환경에 미치는 영향도 고려해야 한다.</span></p>
